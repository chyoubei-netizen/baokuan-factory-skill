# Mode B 写作与复盘流程

## 1. 识别当前阶段

先判断用户要的是：

- 找方向或出选题；
- 把碎片想法整理成稿；
- 改写现有稿；
- 审稿或优化局部；
- 确认后的发布包；
- 发布后复盘。

只完成当前阶段。用户只改开头时，不重新做完整发布包；用户给出完整方向和事实时，不重复做一轮访谈。

## 2. 识别项目并加载最小项目上下文

先按 [项目资料路由规则](项目资料路由规则.md) 识别并确认：`project_id`、`project_name`、`project_scope`（`self` / `client`）与项目别名。依据顺序是当前对话、当前工作目录、用户指定项目、项目简报和本地私有项目资料索引。

不要通过项目名称或人物名字猜测 `self` / `client`。若有多个可能项目，且会导致读错历史稿、套错人设或误用本人表达偏好，只问一句：`这条是给哪个项目/账号写的？`

商业项目创作时，先读取项目简报，确认：身份、目标用户、服务边界、表达风格、禁区和证据条件。项目简报只负责一致性，不代表正文必须出现业务。

从本地私有项目资料索引取得该项目的简报、表达规则、飞书正文来源、内容状态来源、正文匹配键、状态语义、发布数据和案例位置；只读本条所需的最小资料，不混用历史项目事实。若正文或状态链路未配置，继续使用已知简报和事实创作，但将相应的表达学习、历史稿去重或效果学习标记为降级。

### 同时加载个人表达模型

写稿或结构性改写时读取 [个人表达模型](个人表达模型.md)。默认读取所有项目适用的全局操盘偏好、常见负面信号，以及与当前项目相关的少量正/负样本摘要；不加载样本全文。

- `project_scope = self`：再加载本人表达偏好、偏好的推进方式和本人商业露出偏好。
- `project_scope = client`：不加载本人表达偏好；客户的性格、语气、观点强度、禁区和情绪强度只由项目简报或客户人设文件控制。

不要把正负样本全文批量加载，也不要为了满足表达偏好而篡改事实、项目人设或服务边界。本人项目冲突时按以下优先级处理：

```text
当前用户本轮明确要求
>
真实性、项目人设与业务边界
>
本人表达偏好
>
全局操盘偏好
>
账号当前内容策略
>
历史优质样本
>
案例库与爆款机制
>
通用写作习惯
```

客户项目冲突时使用：当前用户明确要求 > 真实性、项目人设与业务边界 > 客户项目表达规则 > 全局操盘偏好 > 账号策略 > 历史稿件 > 案例与爆款机制 > 通用写作习惯。

个人表达模型不是第二套文案模板。要问“这个选题怎样说最自然，同时不违背当前作用域的长期偏好”，而不是要求每条内容满足同一种结构或气质。

## 3. 操盘诊断与问题闸门

先内部判断：

- 本条最适合的主任务：流量 / 信任 / 转化；
- 信任型属于人格信任还是专业信任；
- 素材形态：观点 / 价值观 / 案例 / 工作现场 / 方法 / 经历 / 复盘；
- 目标用户和具体观看理由；
- 用户当前认知阶段：尚未意识到 / 知道但不急 / 想解决 / 正在比较；
- 业务露出：0 / 1 / 2；
- 可用的真实事实和仍缺的证据；
- 适合的平台与预计表达强度。

再向用户给出推荐与理由。缺少会改变稿件方向或真实性的内容时，只问 1—3 个关键问题。详细边界见 [需求清单](需求清单.md)、[商业IP内容决策](商业IP内容决策.md) 和 [文案引擎](文案引擎.md)。

如果用户说“直接写/你判断”，使用保守选择：

- 不确定是否要卖时，先做信任而不是转化；
- 不确定业务连接时，用 0 级而不是硬植入；
- 不确定客户事实时，保留 `【待补充】`；
- 不确定平台时，可先按用户常用平台或通用竖屏口播写，并标明假设。

## 4. 输出方向确认卡

方向仍有分歧或事实缺口时，先给短卡：

```text
推荐任务：
用户认知阶段：
素材形态：
目标用户：
观看理由：
核心观点/冲突：
业务露出等级：
自然体现能力：
真实支撑：
待补事实：
关键问题（最多3个）：
```

若用户给的信息已经完整，方向卡可以压缩为 3—5 行后直接写稿；不要为了流程强行停住。

## 5. 写稿前读取认可稿并做近期内容去重

仅在存在可靠的近期已写、已确认或已发布稿件时执行；没有历史稿就跳过，不为了流程新建记录。

先识别项目，再读取本地私有项目资料索引，确定该项目独有的正文来源、状态来源与匹配规则。不要再用“文档有没有发布”代替“用户是否认可”。默认优先级是：

1. 项目索引配置的 Base/多维表格等状态源：先按项目和“认可状态值”筛出最近约 5—10 条；
2. 按表中的文档链接/token回读项目索引配置的飞书正文；链接缺失时才使用项目内唯一完整标题匹配；
3. 项目索引中明确指定的本地认可稿、脚本或发布归档位置；
4. 用户在本轮对话明确说明满意、认可、可拍、已拍、已发布或已复盘的当前项目稿件。

不默认搜索整个飞书，也不因关键词相似读取其他项目。一个项目可配置多个来源，但每一个都必须在当前项目资料索引中明确归属该项目；读取后按文档 token、记录 ID 或唯一标题合并去重，不扩散到其他项目。

认可状态只决定“用户是否接受这篇文案”。拍摄状态只决定执行进度；发布状态只决定是否上线；发布数据只决定能否学习效果。认可稿可用于表达学习和跨稿去重，未发布不等于未认可。只有已发布且有数据的稿件才能证明效果，优先读取已复盘稿。

飞书不可访问、项目未配置正文/状态来源或无法可靠匹配时，内部标记：`近期认可文案：未成功读取；原因：……；跨稿去重：本次降级执行。` 继续创作，但不得声称已检查过历史内容。

案例库是外部学习样本，不是用户近期内容历史，不用于这一步。没有可靠的日期、状态或项目归属时，不把文件当作“近期内容”使用。

快速比较的不是字面相似度，而是：

1. 开头机制；
2. 核心观点；
3. 论证路径；
4. 使用案例；
5. 内容情绪；
6. 结尾方式；
7. 业务植入方式；
8. 高频句式；
9. 所谓“新认知”是否只是换词。

若开头、论证和结论结构高度相同，判为思路重复，即使行业关键词不同。发现重复后，优先改问题入口、观察对象、论证顺序、信息来源、叙事角度、证明方式、内容任务或结尾作用；不得只换同义词。若改变后仍是同一逻辑，应建议暂缓拍摄，而不是伪创新。

### 表达学习不能变成结构复制

认可稿同时承担两种不同用途：提取稳定的语言气质与判断偏好，以及识别近期已经用过的内容结构。前者可以迁移，后者通常应主动避开。

写稿前内部补一行：`本条独有的思考路径是什么？` 如果答案仍是“现实观察 → 表面解释不够 → 继续追问 → 得到底层模型 → 金句总结”，而近期多篇认可稿已经使用同一路径，就算选题不同也要重新判断结构。可以改变入口、证据顺序、叙述视角、结尾功能，或只讲透一个具体判断；不要为了符合本人“有深度”的偏好，把每条稿件都写成同一种深度思考模板。

## 6. 先搭文案引擎，再找案例

写稿和结构性改写必须先读取 [文案引擎](文案引擎.md)，并在内部完成：

1. 用户认知阶段；
2. 文案事实骨架；
3. 开头锻造卡；
4. 最适合本条的一种证明方式；
5. 与内容任务匹配的正文骨架。

若事实骨架中缺少具体场景、用户原话、过程、案例或数据，优先提问或保留 `【待补充】`；不能用通用痛点和夸张词替代。

## 7. 按需查案例

先扫案例索引，再按以下顺序匹配 1—2 个案例：

1. 目标用户与问题；
2. 内容主任务；
3. 素材形态；
4. 观看机制和信息顺序；
5. 人设与表达强度；
6. 平台；
7. 证据等级。

只提取需要的机制：标题作用、开头任务、信息推进、证据位置、反对意见处理、结尾承接。不要为了“像爆款”拼接多个案例的标志性句子。

聚合库按需读取：

- 改口语或处理书面稿：读取 `口语化表达方式库.md` 相关章节；
- 需要表达动作/感觉增强：读取 `感觉词库.md` 相关章节；
- 需要开头、结构、互动或结尾方案：读取 `写作技巧库.md` 相关章节。

没有匹配样本可继续创作，标注“无直接参考案例，机制待发布验证”。若用户明确要求“基于近期爆款/爆过关键词”，本地证据不足时应实际调研；不能用常识冒充样本。

## 8. 规划标题承诺与观众行为链

先写一句标题承诺：观众点进来后会得到什么。再规划：

1. 谁会停下来；
2. 前几秒用什么具体问题、场景、反差或判断建立期待；
3. 中间如何持续新增场景、事实、判断、情绪、方法或转折；
4. 哪里用经历、过程、细节或数据建立可信度；
5. 观众最可能提出什么反对意见，是否需要回应；
6. 结尾兑现什么、留下什么观点或下一步。

标题、封面和开头可以分工，但不能互相矛盾。小红书优先考虑搜索和点入理由；抖音优先考虑首帧、前 3 秒和节奏；视频号兼顾人物信任与社交传播。

## 9. 写拍摄提纲

提纲至少包括：

- 内容目标与目标用户；
- 一句话核心观点；
- 开头承担的任务；
- 文案事实骨架中的关键场景与证明；
- 场景/问题；
- 事实、过程、案例或判断；
- 转折或反对意见；
- 结尾与业务露出等级；
- 拍摄可执行性和预计时长。

如果真实案例尚缺，不要把示意案例写进正式正文；在提纲标记待补位置。

## 10. 写真人口播稿

写作标准：

- 一句话尽量只表达一个意思，适合分段提词；
- 先具体后抽象，先场景后判断；
- 每段相对上一段有信息或感受推进；
- 允许自然停顿和转折，不追求每段一样长；
- 观点明确但强度匹配证据；
- 不用“首先其次最后”撑结构，不用整齐排比冒充力量；
- 不默认“大家好，我是…”“今天分享三个…”“老板们注意了”；
- 感觉词和口语动作按功能使用，不设数量；
- 0 级内容不植入业务；1 级只自然体现一项能力；2 级先解决购买问题再给一步承接。

先按 [文案引擎](文案引擎.md) 选择流量型、人格信任、专业信任或转化型正文骨架；不要把所有内容写成“痛点—方法—案例—CTA”的同一模板。

表达规则见 [小姜表达机制使用规则](小姜表达机制使用规则.md)。

## 11. 改写专用闸门

改写不是换同义词。先做原文诊断：

- 原文想对谁说、完成什么任务；
- 开头是否给了观看理由；
- 哪些事实与观点必须保留；
- 哪些段落只是重复、书面或自说自话；
- 哪些客户事实不可改写成另一种事实；
- 标题承诺和结尾是否一致。

然后重建信息顺序。若改后仍沿用原段落顺序和论证路径，只换了词或加入几个“其实/本质上”，判为伪改写，重新搭结构。

用户原本有鲜明语气时保留，不要用统一“网感口吻”覆盖本人。

## 12. 二次审稿

从三种视角检查：

### 普通观众

- 我为什么停下？
- 开头是否基于真实场景、明确判断或真实落差？
- 每一段是否有新东西？
- 标题承诺兑现了吗？
- 哪一句难懂、像文章或像培训？

### 目标客户

- 内容说的是我的真实问题吗？
- 我为什么相信？
- 本条的证明方式是否足够、具体且没有夸大？
- 是否出现无证据的案例、结果或能力？
- 业务连接是否自然，有没有突然销售？

### 内容总监

- 主任务、素材形态和结尾是否一致？
- 人设、服务边界和表达强度是否正确？
- 是否同质化、逻辑跳跃或存在平台风险？
- 拍摄者是否能自然说出口并完成画面？

广告感标为低/中/高。中或高必须指出具体句子与修改方式。自审后直接提交修改后的稿，不只列问题。

## 13. 分阶段交付

- 方向未定：只交方向确认卡。
- 方向已定：交拍摄提纲、完整稿、必要画面建议和自审结果。
- 用户确认稿件：读取 [发布物料](发布物料.md) 生成完整发布包。
- 用户明确要“一次完成”且资料足够：可把三阶段合并，但仍按顺序思考。

## 14. 用户反馈沉淀

用户改稿、确认或否定时，先判断反馈级别和作用域，再决定是否更新 [个人表达模型](个人表达模型.md) 或项目简报/客户人设文件。作用域只能是 `global`、`self` 或 `project:<project_id>`；保持内部处理，不额外增加用户填写动作。

### A. 本条局部修改

例如“这句太长”“这里换个词”“这个案例不要”。只修改当前稿，不进入长期规则。

### B. 长期表达偏好

例如“不要每篇都用不是……而是……”“我更喜欢逐层推演”“不要每条都硬转业务”“案例只服务观点”“这种知识博主口吻我不喜欢”。先判定作用域：不编造客户案例等跨项目原则为 `global`；仅本人账号的表达口味为 `self`；某客户的语气、人设或禁区为 `project:<project_id>`。当用户明确表述长期偏好，或同类反馈重复出现时，提炼后追加到相应位置：`global` / `self` 写入 `个人表达模型.md`；项目规则写入该项目简报或客户人设文件。记录日期、用户反馈、具体问题、长期偏好、以后怎样执行、作用域、适用项目、是否长期、证据来源及是否仍需验证。不要照抄整篇废稿，也不要把一次偶发的局部修改升级为长期规则。

### C. 正面样本

用户明确说“这个版本对”“就是这个感觉”“这一版保留”或“这个可以拍”时，先总结其有效原因：开头机制、思考推进方式、观点强度、语言节奏、案例使用和业务露出。只有确有长期迁移价值时，才以对应作用域保留简短摘要：`global` / `self` 写入 `个人表达模型.md`，项目专属样本写入项目资料；不机械保存全文。

若用户明确说“太 AI”“太模板”“观点太浅”“开头像上一条”或“硬植入”，同时判断是否是长期偏好：是则按 B 沉淀；否则只修当前稿。负面样本只保存失败原因和可执行的规避规则，不无限保存废稿全文。

## 15. 发布后复盘

先取得：平台、发布日期、原定任务、播放/曝光、前 3 秒或前 5 秒留存、平均观看、完播、赞评藏转、主页访问、关注、私信/留资/到店/成交，以及同账号同类内容基线。平台拿不到的指标明确写缺失。

复盘时：

1. 对照原任务，不用流量指标单独否定一条信任或转化内容；
2. 判断问题在点入、停留、推进、信任、互动还是承接；
3. 用评论原话和数据支持判断；
4. 给下一条一个可控变量，不同时改十处；
5. 记录哪些机制待验证、哪些可以提高优先级；
6. 只有自有数据相对基线成立时，才标“已验证”。

同时记录 [文案引擎](文案引擎.md) 的模板测试标签：本次假设、只改变的变量、目标用户是否出现、对照基线和下一轮动作。
